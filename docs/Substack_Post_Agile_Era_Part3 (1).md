# Coordinating a Team of Coworking Agents: Multi-Agent Orchestration and the Agent Lifecycle

### Part 3 of a three-part series. What sits above the single-diff pipeline.

*By Deepankar Das | deepankardas.com*

*This is Part 3\. Part 1, "The Post-Agile Era: Building with Co-Working Humans and Agents," diagnosed the problem. Part 2, "Model for Building with Co-Working Humans and Agents: The Agentic Development Model (ADM)," specified the operating model for the single-diff pipeline. This essay covers the questions that sit above the single-diff pipeline: how multiple agents coordinate on the same plan without stepping on each other, how agents themselves are hired, evaluated, versioned, and retired as coworkers, and how the operating model routes work across the lineup efficiently without compromising the disciplines the earlier essays specified.*

---

## Why This Essay Exists

Parts 1 and 2 developed the operating model on the scope of a single diff. One outcome, one context pack, one coding agent, one three-member jury, one Convergence Loop, one commit-attested gate. That scope was chosen deliberately, because the primitives that make the operating model work are most clearly visible at diff granularity, and because a coworking model that does not have a defensible answer at diff granularity has nothing to build on above it.

Real engineering organizations do not run one diff at a time. They run dozens of agents in parallel against the same repository, sometimes against the same plan, sometimes against overlapping surfaces of the same plan, and they run those agents week after week across a lineup that changes as new agents come in and older ones age out. The operating model has to answer three additional questions to be usable at that scale. The first is coordination: when many agents are working the same plan, how does the operating model divide the work, prevent them from stepping on each other, and merge what they produce into a coherent whole. The second is lifecycle: agents are not permanent hires; they are versioned artifacts whose behavior changes with each release, whose fit to a codebase has to be measured before they are trusted with load-bearing work, and whose retirement has to be as disciplined as their onboarding was. The third is routing: which model in the lineup runs which role on which surface at what tier, so that expensive capability is spent where it pays and cheap capability is used where it suffices without compromising the guarantees the earlier essays specified. None of these questions is answered by the diff-level pipeline. All three are answered by the layer above it, and that layer is what this essay describes.

## Multi-Agent Coordination on the Same Plan

The starting point is that the single-diff pipeline in Part 2 is embarrassingly parallel at the diff level, and not at all parallel at the plan level. Two diffs on independent surfaces of the codebase can run through the pipeline concurrently without any coordination beyond what the operating model already provides. Two diffs on the same surface, driven by different agents working different work items from the same implementation plan, cannot. Something has to decide which agent owns which surface at which time, how their work merges, and how the operating model prevents the failure mode where two agents fix the same defect in incompatible ways, or where one agent's refactor invalidates another agent's in-flight assumptions, or where three agents converge on the same file and produce three plausible-looking commits that pairwise conflict and jointly break the invariants none of them individually violated.

That coordination has to be explicit, and it has to live above the coding agent rather than inside it. Coding agents optimize locally, on the work item and surface they were dispatched with. A coordination layer that expects a coding agent to reason globally about the state of other coding agents' work has just moved the coordination problem into a context window that will not hold it. The operating model treats coordination as a distinct role with a distinct artifact.

### The Plan-Level Ownership Map

The primary artifact of the coordination layer is a plan-level ownership map. The ownership map is a repo-resident file, generated from the implementation plan and updated in place as agents are dispatched and as their diffs land. Each row of the ownership map represents an active claim: an agent, the work items it is currently executing, the surfaces of the codebase those work items touch, the context pack it is working from, and the expected window in which the diff is projected to land. The rows are the operating model's view of what agents are currently in flight against the plan.

Before a coding agent is dispatched, its work items are checked against the ownership map. If the surfaces the work items touch overlap with an active claim held by a different agent, the dispatch is blocked. The blocked work either waits for the conflicting claim to close, is rescoped to a non-overlapping subset the plan-level authority approves, or is combined with the conflicting claim into a single larger work item held by a single agent. That decision is made by a named human, the plan-level conductor, whose role is to hold the coherence of the whole plan while the individual coding agents hold local coherence on their assigned surfaces.

The ownership map is not a lock table in the database sense. It is closer to what a build engineer would recognize as a dependency graph annotated with active leases. Every claim carries an owner, an expiry, and a scope. A claim that has been open past its expiry without a landing diff is flagged for the conductor. A claim whose surface turns out to touch more than the coding agent expected produces an expansion request that the conductor either grants or splits. The map is the substrate on which coordination decisions are made and recorded, so that six months later the question of why two agents did not step on each other on a specific week has an answer that lives in a file, not in the memory of the person who managed the week.

### Work Division and Merge Discipline

The implementation plan is decomposed into work items sized to a single coding agent's scope. That decomposition is not incidental; it is the mechanism by which the ownership map remains readable and by which conflicts are avoided in the first place. A work item whose surface cannot be described without listing five modules and three data structures is a work item that has not been decomposed enough. The conductor's first responsibility is to keep the decomposition faithful to the surfaces the codebase actually has, so that ownership is possible to declare and easy to check.

Merge discipline follows from decomposition. When two agents finish adjacent work items whose diffs touch shared files at non-overlapping regions, the merge is mechanical, executed by the operating model's usual tooling, and the commit-attested gate admits each diff on the strength of its own receipt. When two agents finish adjacent work items whose diffs touch shared files at overlapping regions, the merge is not mechanical. The operating model requires that one diff land first, that its receipt be admitted, and that the second agent's diff be rebuilt against the new head, re-run through the Convergence Loop, and re-attested against the new content. There is no fast path that admits a stale diff on the strength of a receipt bound to a superseded base, because such a receipt attests a run that did not verify the code that would actually ship. The commit-attested gate from Part 2 is what makes this discipline enforceable: the receipt is bound to the exact diff, and a diff that no longer matches its receipt cannot pass.

The corollary is that the plan-level conductor pays close attention to which work items are likely to force a re-run. Two agents dispatched simultaneously on work items whose surfaces overlap will produce a rebuild for one of them, which is expensive at agent velocity because the whole Convergence Loop has to re-execute. The dispatch schedule is therefore an optimization problem: land the diffs least likely to invalidate other in-flight diffs first, hold back the diffs whose rebuild cost would be highest, and dispatch new work items into the surfaces least likely to conflict with what is currently in flight. That optimization is what the conductor holds, and the ownership map is the state the optimization runs on.

### The Cross-Diff Convergence Cycle

Some work is not decomposable into cleanly non-overlapping work items. A refactor that changes an API contract touches every caller of that contract. A schema migration touches every reader and writer of the affected columns. A cross-cutting concern like introducing a new observability primitive touches every service that has to emit or consume it. Work of this shape is what the operating model calls a cross-diff outcome. Cross-diff outcomes do not fit the single-diff pipeline, and forcing them into it produces the failure mode where twenty individual diffs land in a sequence that leaves the system in an incoherent intermediate state after each one.

Cross-diff outcomes are handled by a coordination discipline the operating model calls the cross-diff convergence cycle. The plan for a cross-diff outcome is developed as a coherent whole: the API change and every caller update in one plan, the schema migration and every reader-and-writer update in one plan, the observability primitive and every emission and consumption in one plan. The plan is decomposed into work items assigned to individual coding agents, but the ownership map treats the whole set of claims as a single cross-diff bundle rather than as independent claims. The bundle carries its own convergence property: no diff in the bundle is admitted through the commit-attested gate until every diff in the bundle has passed its Convergence Loop and produced a valid receipt, and all the receipts are admitted together as an atomic set. The invariant the operating model protects is that the repository never sees an intermediate state where some callers have adopted the new API and others have not, or where some readers know about the new schema and others do not.

The cross-diff convergence cycle is expensive, because it forces a synchronization point on work that would otherwise be executed independently. It is expensive on purpose. The alternative, which is to land partial cross-diff outcomes and hope the remaining diffs land quickly enough that the intermediate state is not observed, is the shape of the failure the discipline exists to prevent. Cross-diff outcomes are the largest single source of coordination cost in the operating model, and any team that runs the model at scale will invest heavily in decomposing plans in a way that produces as few cross-diff bundles as the codebase's actual structure allows.

### The Agent-to-Agent Coordination Bus

Individual coding agents inside a plan do not talk to each other directly. They talk through the ownership map and through the failure ledger. If agent A needs to know what agent B is currently claiming, it reads the ownership map. If agent A needs to know what rules the operating model has accumulated on the surface it is about to touch, it reads the failure ledger. If agent A produces a signal that agent B needs to react to, that signal is written into the ownership map or the failure ledger, not sent as a direct message.

This routing through shared repo-resident state is deliberate. Agent-to-agent messaging in the direct sense is a coordination pattern that scales poorly and audits worse: it produces conversation logs that were never in the repo, that no receipt attested, and that no rule was written back from. Routing through repo-resident state is slower per exchange, but every exchange is durable, every exchange is auditable, and every exchange lands in a substrate the operating model already treats as load-bearing. The coordination bus is the repo, and the repo is what six months later can answer why one agent's behavior changed in response to another agent's landing diff.

### The Human Conductor's Role

Multi-agent coordination is where the conductor role becomes concrete. Part 2 named the conductor as the senior craft the post-Agile organization promotes into. This essay is where that promotion path acquires its specific content. The conductor holds the plan-level ownership map, adjudicates dispatches that would conflict with in-flight claims, decomposes work into work items sized to a single coding agent, calls the cross-diff convergence bundles, and holds the coherence of the plan while the individual coding agents hold local coherence on their surfaces. The conductor is not writing code. The conductor is not reviewing individual diffs, because the three-member jury and the Convergence Loop are what review diffs. The conductor is holding the plan. That is a full-time role, and it is the role that scales the operating model past the point where a single engineer with a single coding agent can run it end to end.

The conductor's tools are the ownership map, the failure ledger, and the delivery dashboard from Part 2\. The conductor's rhythm is not the morning briefing of Part 2, which is the local view; it is the plan-level check-in, which is the aggregation view. The conductor's failure mode is the same failure mode the operating model as a whole guards against: losing coherence at the layer of aggregation when the individual layers are all locally correct. The primitives of Part 2 keep individual diffs correct. The coordination discipline of Part 3 keeps the plan they collectively execute coherent.

## The Agent Lifecycle: Hire, Evaluate, Version, Retire

The second question this essay answers is how agents themselves are treated as coworkers, not as tools. A tool is picked up and used. A coworker is onboarded, evaluated in role, given more responsibility as trust accrues, versioned as its capabilities evolve, and retired when its fit to the work has run out. The operating model treats coding agents the second way, because treating them the first way is what produces the failure mode where a model release quietly changes behavior on the same prompt, a codebase that had converged its Convergence Loops to two iterations starts requiring six, and no one on the team can explain why because no one was tracking the agent as an entity separate from the prompts it was running.

### Onboarding a New Agent

A new agent enters the operating model through a specific procedure. Adding a new agent to the lineup is not a matter of adding an API key to a config file, though that is the smallest mechanical piece. Onboarding an agent means running it against a defined evaluation corpus that reflects the codebase and the plans the agent will actually be dispatched against, comparing its behavior to the incumbent agents on the same corpus, deciding which classes of work it is stronger and weaker at than the incumbents, and writing a routing rule into the operating model that dispatches specific classes of work to the new agent based on that measured fit.

The evaluation corpus is what makes onboarding rigorous rather than impressionistic. Every team running the operating model at scale accumulates an evaluation corpus over time: a curated set of past outcomes, each with its context pack, its acceptance criteria, and the known-good diff that closed it. A new agent is run against this corpus and produces its own set of diffs, which are compared to the known-good diffs on convergence iteration count, jury finding rate, RADAR selection quality, escalation rate, and time-to-terminate. The comparison produces a scorecard that positions the new agent against the incumbents by defect class and surface class. That scorecard is what the routing rules are written from.

Onboarding is not a one-time event. A new model version from the same vendor is a new agent for the purposes of the operating model. The scorecard is re-run against the same evaluation corpus. The routing rules are re-evaluated. If the new version scores worse than the outgoing version on a class of work, the routing keeps the outgoing version for that class until the newer version catches up or the outgoing version is retired for other reasons. The operating model treats model releases as coworker turnover, because that is what they are, and it responds with the same rigor it would apply to a human coworker whose job scope was changing.

The comparison inside the evaluation corpus deserves a specific caution. When a new version produces a diff that differs from the known-good diff on a past outcome, the difference is not, by itself, evidence the new version is worse or better. Two competent implementations of the same acceptance criteria can differ substantially in structure, factoring, and style while both being correct. What the scorecard measures is whether the new-version diff satisfies the same acceptance criteria, converges in the same or fewer iterations, produces the same or lower jury finding rate, holds the same critical-invariant floors under RADAR, and terminates in the same or shorter time. Stylistic and structural divergence from the known-good diff is not scored against the new version. If the operating model scored aesthetic match, the evaluation would lock the lineup into whichever version happened to be first and would penalize every real capability gain that arrives with a different aesthetic. What matters is that the outcome is closed correctly, not that it is closed identically.

### Evaluation In Role

Onboarding scorecards are the entry evaluation. In-role evaluation is continuous, because a coding agent's behavior against a fixed evaluation corpus does not fully predict its behavior against the living codebase whose invariants and surfaces are changing week over week. The operating model collects per-agent metrics from the run folders as a matter of course: convergence iterations per diff, jury findings per diff by defect class, RADAR-flagged regressions per diff, escalation rate per diff, and time-to-terminate per diff. These metrics are aggregated at the agent level, broken down by surface class and defect class, and rendered in a per-agent performance view that a plan-level conductor can read.

Drift in these metrics is a signal, not a verdict. An agent whose escalation rate rises on a specific surface class over a specific window may be reacting to a change in the underlying code that the operating model has not yet reflected in its context packs, or it may be experiencing a genuine capability regression. The conductor's job is to investigate the drift, distinguish between the two, and act accordingly: either update the context pack template for the affected surface, or adjust the routing rules to steer that surface class away from the drifting agent, or open a retirement review for the agent if the drift is broad enough that no single adjustment restores fit.

The metrics also feed positive routing changes. An agent whose convergence iteration count on a specific defect class drops meaningfully over a window has demonstrated capability the routing rules should exploit. Routing an agent to the work it is best at is the operating model's version of assigning a coworker to their strengths. The scorecards and the per-agent performance view are the mechanism that keeps those assignments defensible rather than intuitive.

### Versioning and Attribution

Every diff the operating model admits carries, in its run folder, the model identifier and version of the coding agent that produced it and every juror that reviewed it. Part 2 named this as part of the attribution and audit substrate. This essay is where the version identifier becomes operationally load-bearing, because it is what makes the agent lineup analyzable as a set of versioned entities rather than as a moving average of vendor behavior.

The operating model pins agent versions explicitly. A team running the operating model does not run whichever version of a coding agent the vendor happens to be serving on any given day. It runs a version it has evaluated, scored, and admitted to the lineup, and it pins that version until a newer version has cleared the same evaluation. Vendor releases are received as candidates, evaluated against the corpus, and either promoted into the lineup or held back. This discipline is what prevents the failure mode where a silent vendor rollout changes agent behavior overnight and the team's Convergence Loop iteration counts drift for weeks before anyone connects the drift to the rollout.

Version pinning also makes rollback possible. If a promoted version turns out to have a regression the evaluation did not catch, the routing rules can revert to the previous version while the regression is investigated. Rollback in software has been standard practice for two decades on production services. Rollback on the agents that write software has to be standard practice on the same reasoning. The operating model treats the agent lineup with the same version discipline it treats any other production dependency, because that is what the agents functionally are.

### Shipped Code Is Not Up for Re-Litigation

Versioning the agent lineup creates a failure mode the operating model has to name explicitly and defend against, because it is invisible until it has already cost a team a quarter. The failure mode is this: a diff was written last quarter under agent-v1, converged cleanly, passed the jury, cleared RADAR, was admitted through the commit-attested gate, and has been running in production without incident. Agent-v2 is promoted into the lineup. Somewhere downstream, that code enters a new agent's context again, whether because a nearby feature is being built, a refactor sweeps the surface, an in-role evaluation replays a corpus that includes it, or a jury on a new diff cross-reads the older code as part of understanding the change. Agent-v2 reads the older code, disagrees with it stylistically, structurally, or on some judgment call agent-v1 made, and flags it. In the worst case, the flag becomes a work item, the work item becomes a diff, and code that was working perfectly gets rewritten to satisfy a preference that never existed when the code was written.

This is not hypothetical. Two model versions from the same vendor already disagree with each other on stylistic and structural questions on any non-trivial codebase, and two model versions from different vendors disagree more. A lineup that treats every such disagreement as a defect will consume itself churning working code every time a new version is promoted. The operating model refuses to pay that cost, and it does so by naming a specific principle: shipped code is not up for re-litigation by a new agent version unless something external justifies opening it.

The principle is enforced through three mechanisms. The first is the version-of-record on every shipped diff. The run folder from Part 2 already carries the agent version that produced the diff. What the operating model states additionally is that the shipped diff is treated as authored under that version's judgment, and a later agent version's disagreement with that judgment is not, on its own, a defect. A new-version finding against old code is admissible only if it names an external cause: an invariant that has since changed, a failure-ledger rule that has since been written, a security advisory that has since landed, a dependency that has since been deprecated, a specification that has since been updated, or an observed production incident. Absent one of those causes, the finding is closed as an out-of-scope opinion, not opened as a work item. That closure is itself recorded, so the pattern of what the new version wanted to reopen becomes visible without the reopening actually happening.

The second mechanism is scope-of-change discipline on the coding agent. A coding agent's write authority is bounded to the surfaces its current work item authorizes. Adjacent code the agent reads as context is read-only for the current diff, no matter how strongly the newer version feels about it. If the agent believes an adjacent surface needs work, it files a separate work item with a named external cause, and that work item enters the plan through the normal specification pipeline where the plan-level conductor decides whether to schedule it. This is the discipline that prevents the failure where an agent dispatched to touch file A ends up rewriting files B, C, and D because a newer version thinks it can do better. The commit-attested gate reinforces this from the other direction: a diff whose changes extend beyond the surfaces its work item authorized fails the receipt binding on scope grounds and does not admit.

The third mechanism is treating cross-version disagreement as a lineup-health signal rather than a code-quality signal. When new-version findings against old code accumulate at high rate for a specific version pairing on a specific surface class, that is diagnostic about the two versions' calibration relative to each other, not about the codebase. The signal goes into the per-agent performance view described earlier in this section. It may inform routing rules, so the new version is steered away from surfaces where its disagreement rate is highest. It may trigger a re-evaluation of the new version's fit if the pattern is broad enough. It does not become a backlog of rewrites. Model-driven churn is a category of cost the operating model refuses to pay, and the mechanism that refuses it is naming the finding as a lineup-health datum rather than a defect ticket.

The principle also has a positive form. Code that was working perfectly under an older agent version has, by that fact, demonstrated fitness against the acceptance criteria and against the invariants the operating model protects. Rewriting it under a newer version's aesthetic risks introducing regressions the original code was known not to have, spends token budget on a change with no external cause, and consumes reviewer attention the operating model treats as its scarcest resource. The default posture toward working shipped code is to leave it alone. Change requires cause. That posture is what makes lineup evolution safe over time.

### Retirement

Agents are retired for one of three reasons. The first is capability succession: a newer version has scored better on the evaluation corpus across the classes of work the outgoing version was routed to, and the routing rules have shifted the outgoing version's work to the new version. The retirement is announced, the outgoing version is held in the lineup for a window in case the succession has to be reversed, and the version is decommissioned when the window closes without a rollback.

The second is capability regression: a version whose in-role metrics have drifted beyond a threshold the operating model has declared for a class of work, and whose drift cannot be recovered by context-pack updates or routing adjustments. The retirement is again announced, the affected work is re-routed to remaining agents in the lineup, and the version is decommissioned when the re-routing has been verified.

The third is discontinuation: the vendor has stopped serving the version, or the operating model has decided the vendor as a whole no longer fits the lineup. This is the most disruptive retirement because it forces re-routing of everything the version was handling. The operating model treats vendor concentration as a risk the lineup is designed to hedge against, which is why the three-member jury draws from three different foundational-model families in the first place. A jury and a lineup that had collapsed to a single vendor would find vendor discontinuation existential. A lineup deliberately diverse across vendors finds it disruptive but survivable.

Retirement in every case is a written procedure with a record. The run folders that carry the retired version's identifier remain valid; the receipts remain verifiable; the archive from Part 2 continues to answer six-months-later questions with the same fidelity it did before the retirement. What changes is only the forward routing. Nothing that has already shipped becomes unattributed because the agent that produced it is no longer in the lineup.

## Efficient Model Routing Across the Lineup

The third question this essay answers is how the operating model routes work across the lineup efficiently. Coordination decides which agent works which surface. Lifecycle decides which versions are in the lineup at all. Routing decides which of the admitted versions actually runs each role of each work item, at what tier, and under what fallback rules when the preferred version is unavailable. Routing is where operational cost is set. It is also where cost pressure most often collides with the disciplines the earlier sections specified, so the routing paradigm has to be designed to make those collisions impossible rather than merely discouraged.

The starting point is that the phrase "model routing" gets used loosely in the market. Sometimes it means cost-tier routing, sending easy prompts to cheap models and hard ones to expensive ones. Sometimes it means capability routing, sending code review to model A, code generation to model B, planning to model C. Sometimes it means latency routing, sending interactive work to the fastest model and batch work to whichever is cheapest at the moment. Sometimes it means vendor-availability routing, falling back to a secondary vendor when the primary is rate-limited or down. All four are real, and all four get conflated. The operating model treats them as three composable layers with their own artifacts, their own owners, and their own failure modes.

### What the Operating Model Refuses to Route On

Some roles are load-bearing on capability and are not open to cost-driven routing. Naming them first, before the routing paradigm proper, is what keeps the paradigm honest.

The three jurors of the Cross-Model Convergence Review are load-bearing. Jury quality is the single largest determinant of Convergence Loop iteration count on defect-rich diffs, because a cheaper juror that misses a finding does not save the operating model money; it costs the operating model an extra loop iteration, and an extra loop iteration is orders of magnitude more expensive than the model dollars saved on the juror. The three jurors are also required to come from three foundational-model families as a diversity floor, which forecloses the routing shortcut that would consolidate the jury on a single vendor for volume discounts. Any routing rule that would violate the three-family jury floor is refused at the manifest layer described below.

The coding agent on a diff touching a critical-invariant surface is load-bearing. A cheap coding agent on a payments module, an access-control module, a schema-migration module, or any other surface whose invariants are declared critical is exactly the false economy the operating model exists to prevent. Critical-invariant surfaces are named explicitly in the routing manifest, and coding-agent dispatches on those surfaces are restricted to the top tier of the lineup.

The adjudicator model, if the operating model uses one to resolve jury disagreement before human escalation, is load-bearing. Cheapening this creates the failure mode where mediocre adjudication produces bad rules that the failure ledger honors forever, so the same disagreement produces the wrong outcome every time it recurs. The adjudicator is either top-tier model capability or a human. The operating model does not admit a middle option.

### The Routing Manifest

The routing manifest is a repo-resident, version-controlled, human-owned file that declares, for every role the operating model dispatches, the tier requirement that role must satisfy. Tiers are declared abstractly (top, mid, cheap) and mapped to specific model versions elsewhere so that a lineup change updates the mapping without rewriting the manifest. The manifest is the artifact the runtime consults before every dispatch. A routing decision that would place a role on a version below its declared tier is refused at dispatch time and logged. This is what makes the "load-bearing roles not routed on cost" commitments in the previous subsection enforceable rather than aspirational.

A representative manifest looks like this. Every ADM operating model instance will tune the specific assignments, but the shape is the same.

- **Jury juror**: top tier. Three foundational-model families minimum across the panel of three. No fallback to lower tier.  
- **Coding agent on critical-invariant surfaces**: top tier. Surfaces enumerated by name in the manifest and inherited from the specification's invariant declarations.  
- **Coding agent on non-critical surfaces**: mid tier acceptable. Top tier permitted when fit scores justify it.  
- **Adjudicator on jury disagreement**: top tier or human.  
- **RADAR test-selector**: mid tier with a corpus-verified false-negative rate on critical invariants below a declared threshold. Cheap-tier candidates are admissible only if they clear the same threshold on the evaluation corpus.  
- **Context-pack search-and-summarize scaffolding**: cheap tier. This is scaffolding a human uses to assemble a pack, not the pack itself. The pack is human-authored.  
- **Escalation triage**: cheap tier. The task is classifying an escalation payload to the class of human who should answer it, which is bounded and low-stakes.  
- **Failure-ledger rule authoring assistance**: cheap tier. The adjudicator decision is what the rule expresses; a cheap model can format the rule with correct scope, owner, and expiry once the decision is made.  
- **Documentation, comments, and commit-message generation from an already-attested diff**: cheap tier. The diff has already passed the gate, so the downstream artifacts are definitionally low-stakes.  
- **Delivery-dashboard narrative generation from structured metrics**: cheap tier.  
- **Convergence Loop code-fix iterations after the first, on non-critical surfaces, for findings classified as trivial**: cheap tier permitted, top tier still acceptable. Findings are classified as trivial when they match declared categories such as formatting, linting, name changes, and comment updates. Any finding not on the trivial list holds the fix iteration at the same tier as the original coding agent.  
- **Convergence Loop code-fix iterations for structural findings, invariant-touching findings, or any finding on a critical-invariant surface**: same tier as the original coding agent. No cheap-tier substitution.

The manifest is not a fixed table. It is a declaration the operating model owns, and it evolves as the lineup evolves and as the failure ledger accumulates evidence about where routing shortcuts hold and where they do not. A change to the manifest is itself a diff that flows through the operating model's own pipeline: proposed, reviewed, admitted through a gate, and versioned. That is what keeps the manifest defensible six months later when a specific dispatch is questioned.

### Fit-Based Routing Within a Tier

Within the tier a role requires, the specific model version dispatched is chosen by scored fit for the surface class and defect class of the current work item. This is what the lifecycle section commits to already, and this subsection is where the commitment becomes operational.

The inputs to fit-based routing are the onboarding scorecard from the evaluation corpus and the in-role metrics from the run folders. For a given work item, the routing runtime reads the work item's surface class and defect class, queries the per-agent performance view for the tier the manifest requires, and dispatches to the version with the strongest scored fit for that combination. Ties are broken by recency of the scoring evidence, which is to say the version with the more recent strong-fit evidence is preferred over the version whose strong-fit evidence is older and may not reflect the current codebase.

The dispatch is logged with the tier requirement satisfied, the fit score at time of dispatch, the version chosen, and the alternative versions considered with their scores. Six months later, the question "why did model X get this diff on this day when model Y was the higher-scoring option" is answered by reading the dispatch log the same way the run folder answers who wrote the code. Routing decisions become another auditable substrate rather than a black box in the runtime.

Fit-based routing also feeds back into onboarding evaluation. A new version's scorecard is not a one-shot artifact; every dispatch and its outcome updates the version's fit score for the surface class and defect class of that dispatch. Over time, the version whose actual in-role performance diverges from its onboarding scorecard is re-scored, and the routing rules adjust to reflect the divergence. This is what keeps routing calibrated to reality rather than to whichever week the evaluation corpus was last run.

### Availability and Cost-Aware Fallback

Within the tier and within acceptable fit, the runtime chooses among admissible versions on availability and cost. If the preferred version is rate-limited, the runtime falls back to the next-best-fit version at the same tier. If several versions are available at similar fit, the runtime prefers the one that is currently cheapest at similar latency. This is the layer where actual cost savings compound at scale.

The rule that governs this layer is queue-rather-than-degrade. If the whole tier is unavailable for a vendor, the work queues rather than falling back to a cheaper tier that the manifest does not permit for the role. Silent degradation of tier under load is the failure mode the layer is designed to prevent, because a load-driven cheap-tier substitution on a critical-invariant coding agent is exactly the shortcut the top of this section refused. The queue is finite and monitored; a queue that grows beyond a declared threshold is escalated to the plan-level conductor rather than resolved by lowering the tier. That escalation gives the conductor the choice to either wait, or explicitly authorize a lower-tier dispatch with the authorization logged in the dispatch record, or reschedule the work.

Latency routing rides on this layer as well. Interactive roles, such as context-pack scaffolding driven by a human sitting in front of a screen, are latency-preferred within their tier. Batch roles, such as overnight documentation generation on already-shipped diffs, are cost-preferred within their tier. The latency preference is a property of the role, declared in the manifest, and the availability-and-cost layer respects it.

### How the Three Layers Compose

Layer one, the manifest, is the human-owned declaration of what tier every role must satisfy. It changes on the timescale of the operating model itself, which is to say deliberately and with review.

Layer two, fit-based routing within a tier, is the operating model's continuous choice of which specific version inside an admitted tier is dispatched for a given work item's surface and defect classes. It changes on the timescale of onboarding scorecards and in-role metrics, which is to say weekly to monthly.

Layer three, availability and cost-aware fallback within tier and fit, is the runtime's per-dispatch choice given current vendor availability, rate limits, and pricing. It changes on the timescale of vendor operations, which is to say minute to minute.

The three layers do not shortcut each other. Layer three cannot violate layer one, because layer three's search space is bounded by what layer one admits. Layer three cannot violate layer two, because within-tier fallback is required to remain within acceptable fit for the surface class and defect class. Layer two cannot violate layer one, because the fit search inside a tier only considers versions the manifest admits at that tier. This is what makes the paradigm efficient without being fragile: aggressive cost optimization at layer three does not compromise the capability floor set at layer one or the calibration set at layer two.

### Composition With the Rest of the Operating Model

The routing manifest joins the failure ledger, the ownership map, and the run folder as a first-class artifact the operating model persists in the repo. Every routing decision is auditable because every dispatch is logged. Every manifest change is auditable because the manifest is a versioned file whose changes flow through the operating model's own diff pipeline. Every fit score is defensible because the scoring evidence lives in the evaluation corpus results and the per-agent performance view.

The version-pinning discipline protects routing against silent vendor changes. A vendor rollout that would place a new model version behind the same API name is caught by the pinning, evaluated against the corpus, and either promoted into the manifest at some tier or held out until it clears evaluation. The cross-version re-litigation defense protects routing against the failure mode where a cheap-tier fix on a Convergence Loop iteration is later flagged by a top-tier juror on the next diff and rewritten for aesthetic reasons. The three-family jury floor protects routing against the temptation to collapse the jury on cost grounds. And the queue-rather-than-degrade rule protects routing against load-driven silent-degradation of tier.

Routing is where the operating model spends its capability budget deliberately. Every dollar spent on top-tier capability where the manifest requires it is a dollar that buys the disciplines the earlier essays specified. Every dollar saved by cheap-tier routing on roles the manifest permits it is a dollar the operating model does not pay for capability it does not need. The paradigm is efficient because it draws the line between those two categories explicitly, records where each dispatch fell, and refuses to let cost pressure move the line without a manifest change that flows through the same review discipline as the code.

## Composition With the Single-Diff Pipeline

The coordination, lifecycle, and routing disciplines in this essay compose with the single-diff pipeline in Part 2 in a specific way. The single-diff pipeline is the mechanism that produces trustworthy diffs one at a time. The coordination discipline is the mechanism that runs the single-diff pipeline in parallel across many agents on the same plan without producing incoherent aggregate state. The lifecycle discipline is the mechanism that keeps the agent lineup itself trustworthy over time, so that the guarantees of the single-diff pipeline hold across model releases, vendor rollouts, and turnover in the lineup. The routing discipline is the mechanism that spends the operating model's capability budget deliberately across the lineup, so that top-tier capability lands where it earns its cost and cheap-tier capability handles the roles where it suffices.

None of these layers substitutes for another. A team that has adopted the single-diff pipeline without the coordination layer will find its Convergence Loops running clean at diff granularity while the plan they collectively execute drifts into incoherence at the aggregate level. A team that has adopted the coordination layer without the lifecycle layer will find its ownership map and its cross-diff convergence bundles working correctly against a lineup whose behavior is silently drifting under it. A team that has adopted the lifecycle layer without the routing layer will have a well-versioned, well-evaluated set of agents that either burn top-tier capability on cheap-tier roles or, worse, cheap out on load-bearing roles under cost pressure and lose the disciplines the earlier layers built. The four layers, the diff-level pipeline of Part 2 and the coordination, lifecycle, and routing disciplines of Part 3, are the operating model as a whole. The three parts of this series are those four layers.

## The Bottom Line for Part 3

The single-diff pipeline of Part 2 is the mechanism the operating model uses to make each diff trustworthy. The coordination layer of Part 3 is the mechanism it uses to make the plan those diffs collectively execute coherent. The lifecycle layer of Part 3 is the mechanism it uses to keep the lineup of agents that runs the plan itself trustworthy across model releases and vendor turnover. The routing layer of Part 3 is the mechanism it uses to spend its capability budget deliberately, top tier where the manifest requires it, mid tier where fit and threshold allow it, cheap tier where the roles are definitionally low-stakes, and never below tier under load. Coordination is held by a named human, the plan-level conductor, on a plan-level ownership map that lives in the repo. Cross-diff convergence bundles are the discipline that keeps refactors, migrations, and cross-cutting concerns from producing incoherent intermediate states. Agent-to-agent coordination routes through repo-resident state rather than direct messaging, so that every coordination signal is durable and auditable. Agents are onboarded through evaluation against a curated corpus, evaluated in role through per-agent metrics from the run folders, versioned explicitly with pins the operating model controls rather than defaults the vendor controls, protected from re-litigation of shipped code without external cause, and retired through a written procedure that preserves attribution on everything the retired version shipped. Routing is governed by a versioned manifest that declares tier requirements per role, refined by fit-based dispatch within tier, and executed by availability-and-cost-aware fallback that queues rather than degrades under load.

The scope note that closed Part 2 named one topic still outside the coworking series, which is the runtime authorization layer. That topic remains outside this essay as well, for the same reason: it is a security-architecture question rather than a coworking question, and it deserves its own dedicated treatment. Everything else the coworking model has to answer, this three-part series has answered.

Agile did not fail. Its contract expired. The Agentic Development Model is the replacement contract for coworking teams. Part 1 diagnosed the problem. Part 2 specified the operating model at the diff level. Part 3 specified the coordination, lifecycle, and routing disciplines that let the diff-level operating model run at organizational scale. The whole model is on the page now. If it resonated, use it. If it did not, tell me why. The model is still improving, and it improves fastest against real feedback from teams running it.
